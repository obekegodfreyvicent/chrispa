# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

**ChrisPa Scents and Soaps LTD** — a Kampala, Uganda-based natural wellness e-commerce brand solving the lack of access to natural, chemical-free products for personal care, home cleaning, and culinary needs (candles, sea salts, ghee, honey, soap bars), sourced from local ingredients (goat's milk, honey, herbs, ghee, soywax, beeswax, sea salt, essential oils). `docs/SRS.md` is the Software Requirements Specification — read it before implementing new features; it defines functional requirements (FR-IDs, traced back to the original wireframes), the data model, API surface, and target technical stack. `mockUps/` holds the original static HTML wireframes the SRS and app were built from (see below).

npm workspace monorepo:

- `apps/api` — NestJS + Fastify backend (PostgreSQL via Prisma, Redis, JWT auth)
- `apps/storefront` — Next.js 16 customer storefront (App Router)
- `apps/admin` — Next.js 16 admin/back-office console (App Router)

## Commands

Run from the repo root unless noted.

```
npm install                          # installs all three workspaces
docker compose up -d                 # starts local Postgres (:5440) and Redis (:6380)
cp apps/api/.env.example apps/api/.env
npm run prisma:migrate               # applies the Prisma schema to the local DB
npm run db:seed                      # populates the real ChrisPa catalog/demo data — see below
npm run dev:api                      # http://localhost:3000/api/v1
npm run dev:storefront               # http://localhost:3001
npm run dev:admin                    # http://localhost:3002
```

**Seed data** (`apps/api/prisma/seed.ts`, idempotent via `upsert`): 5 product lines, 25 SKUs (24 `ACTIVE` + 1 `DRAFT`, matching the wireframes' names/prices/copy where shown), 6 wellness tags, 2 warehouses with inventory records (including the exact low-stock numbers from the Admin Inventory wireframe), 3 coupons, 1 bundle, 4 social media accounts (Instagram/Facebook/TikTok/WhatsApp, placeholder handles), 5 staff users (`chris@chrispa.ug` / `patricia@chrispa.ug` / `dennis@chrispa.ug` / `grace@chrispa.ug` / `brenda@chrispa.ug`, password `ChrisPa2026!`, roles Owner/Store Manager/Fulfillment/HR Manager/Support Agent) each with a matching `Employee` record, a 6th `Employee` with no linked login (demonstrates HR holding a record pre-onboarding), 4 departments, one approved leave request, one completed clock-in/out cycle, and one shift (for the Phase 2 HR features), and a sample Gold-tier customer (`sarah@example.com`, same password) with order history and a loyalty ledger. If the DB already has conflicting rows (e.g. a test user registered by hand before seeding), `upsert`'s `update: {}` branches won't overwrite them — reset with `cd apps/api && npx prisma migrate reset` for a clean slate. **That command is destructive and Prisma's CLI will refuse to run it for an AI agent without the user's explicit, freshly-given consent** (`PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` must be set to the verbatim text of that consent) — always ask first, never assume approval from earlier in a conversation.

Postgres/Redis are mapped to **5440/6380, not 5432/6379** — this dev machine already runs other projects' Postgres/Redis on the standard ports. Check `docker ps` before assuming default ports are free on a new machine.

Per-workspace commands (build, lint, test) live in each app's own `package.json`; run them via `npm run <script> --workspace apps/<name>`, or `cd` into the app first.

## Architecture

- **`apps/api/prisma/schema.prisma`** is the source of truth for the data model — matches SRS §9. Run `npm run prisma:migrate` (wraps `prisma migrate dev`) after changing it. Conventions used throughout: UUID PKs, `@db.Timestamptz(3)` on every `DateTime` (Prisma defaults to timezone-naive `timestamp` on Postgres, which this schema deliberately avoids), and explicit `@@index` on every foreign key not already covered by a `@unique`/`@@unique` — Prisma does **not** add those automatically on the `postgresql` provider. `Product.stockQty`/`Variant.stockQty` are denormalized read caches, not the source of truth — `InventoryRecord` (per product × warehouse) is; nothing keeps them in sync yet (see the comment on `Product.stockQty` in the schema).
- **`apps/api/prisma.config.ts`** configures the Prisma CLI (schema path, seed command) — Prisma 6+'s replacement for the deprecated `package.json#prisma` field. It explicitly loads `.env` via `process.loadEnvFile()` since Prisma's config-file mode disables its old auto-dotenv behavior for CLI commands (Prisma Client's own runtime still auto-loads `.env` independently, which is why this was easy to miss during development).
- **Module layout** (`apps/api/src/modules/*`) mirrors the SRS's FR groups: `auth`, `catalog`, `cart`, `orders`, `inventory`, `crm`, `marketing`, `cms`, `loyalty`, `support`, `admin-users`, plus `hr` (see below — not part of the original SRS/wireframes, added later as a separate internal-tooling module). Each is a self-contained Nest module (controller + service, sometimes `dto/`).
- **Auth** is the one fully end-to-end module: register/login/refresh/**logout**/**change-password** with JWT (access + rotating refresh tokens, hashed at rest), a `JwtAuthGuard` for authentication and a `RolesGuard`/`@Roles()` decorator for RBAC. `UserRole` (`OWNER`, `STORE_MANAGER`, `FULFILLMENT`, `SUPPORT_AGENT`, `HR_MANAGER`, `CUSTOMER`) gates the `/admin/*` routes. **Refresh tokens are hashed with SHA-256, not bcrypt** — bcrypt silently truncates its input at 72 bytes, and these JWTs share an identical prefix (header + `sub` claim) well past that length for a given user, so hashing them with bcrypt made every refresh token issued to the same user collide onto the same truncated hash: any of a user's active tokens would "match" any other, silently defeating both rotation and revocation. This was live and unnoticed until logout was added and tested — if you ever need to hash a high-entropy token/secret again, use `createHash('sha256')` (or similar), not bcrypt; bcrypt is for low-entropy human-chosen passwords specifically. The storefront's `SiteHeader` reflects real auth state (Log In vs Log Out) by checking `getAccessToken()` on mount — it relies on the `(auth)`/`(site)` route-group split remounting the header after login/logout; `lib/auth-client.ts`'s `logout()` calls the API (revokes server-side) before clearing local tokens, never throws, and always leaves the client in a logged-out state even if the request fails. Both frontend apps' `authedFetch()` now also **auto-refreshes on a 401**: access tokens are short-lived (15 min, `JWT_ACCESS_TTL`) and there's no other recovery path, so without this every write action would silently start failing partway through a session — it collapses concurrent 401s into one shared refresh call (`inflightRefresh`) since the refresh token rotates on each use and firing two at once would invalidate each other.
  - **Forced password reset for staff-issued logins**: when Executive (`OWNER`) or Human Resources (`HR_MANAGER`) creates an employee with `loginEmail`/`loginRole` (or grants a login to an existing one via `POST /hr/employees/:id/create-login`), `EmployeesService.createLoginInternal()` generates a one-time temporary password (`common/util/temp-password.util.ts`, `crypto.randomInt`-based, no ambiguous chars), hashes it, and sets `User.mustChangePassword: true` — the plaintext is returned **once**, in that API response only, never stored or logged, since there's no email/SMS delivery channel to send it through (same constraint noted elsewhere for OTP/invites). The flag rides in the JWT payload (`AuthService.issueTokens()`) and is enforced globally by `MustChangePasswordGuard` (registered via `APP_GUARD` in `app.module.ts`, so it can't be forgotten on a new module) — it blocks *every* endpoint except `/auth/change-password`, `/auth/logout`, and `/auth/me` (marked with `@AllowPendingPasswordChange()`) until the temp password is replaced. That guard deliberately only *decodes* the JWT's claim (no signature verification, no DB call) — `JwtAuthGuard` still verifies the signature per-controller afterward, so a tampered token just gets rejected there regardless of what the decode-only check decided. `POST /auth/change-password` verifies the current password, clears the flag, and reissues tokens immediately (no waiting out the old token's TTL). Only an `OWNER` can grant the `OWNER` role through this flow — `HR_MANAGER` is blocked from minting new Owner accounts (`ForbiddenException` in `EmployeesService`). Frontend mirrors this: `getMustChangePassword()` (JWT-decode, same pattern as `getUserRole()`) drives a redirect to `/change-password` from both the login page and `AdminShell` — real enforcement is still server-side, this just avoids landing on a page full of failed requests.
- **Checkout** (`apps/api/src/modules/checkout`) is the other end-to-end module: validates the cart, checks per-warehouse stock (FIFO across batches), computes pricing (delivery fee + optional coupon), creates the `Order`/`OrderItem`s inside a single `$transaction`, decrements inventory, awards loyalty points, and clears the cart. Only `CASH_ON_DELIVERY` actually completes — `MOBILE_MONEY`/`CARD` return 501 until a payment gateway is chosen (see the comment atop `checkout.service.ts` for the concurrency caveats that come with its current single-warehouse, no-sequence-table design).
- **Admin Product Manager** (`apps/api/src/modules/catalog/admin-products.controller.ts` + the same module's `CatalogService`) is the third end-to-end module: full CRUD at `/admin/products` (OWNER/STORE_MANAGER only), with full-replace semantics for wellness tags and media URLs, auto-slug generation with collision handling, and archive-instead-of-delete for any product with real order history (hard-delete would violate the `OrderItem` → `Product` foreign key by design — that's what protects order history from being silently corrupted). Product media is a **real upload**, not a pasted-URL placeholder — `POST /admin/products/media/upload` (multipart, JPEG/PNG/WEBP/GIF, 5MB cap) writes to `apps/api/uploads/products/` and returns a URL, the same local-disk pattern (and same lack of object-storage/CDN integration) as the customer avatar upload at `POST /account/profile/avatar`; the Add/Edit Product form uploads each selected file immediately and adds the returned URL into `mediaUrls`, which still saves with full-replace semantics. **Gotcha if you touch this code**: `CatalogService.getByIdForAdmin()` takes an optional Prisma client argument specifically so it can be called with `tx` from inside `createProduct`/`updateProduct`'s `$transaction` — calling it with the default (outer, non-transactional) client from inside a transaction will throw `NotFoundException` on an uncommitted row and silently roll back the whole write. Hit this exact bug once already; if you add a third transactional write path here, pass `tx` through the same way.
- **Admin Order Management** (`apps/api/src/modules/orders/admin-orders.controller.ts` + `OrdersService`) is the fourth end-to-end module: `/admin/orders` list (status filter, search, per-status counts for the tab UI) and a status-transition endpoint (OWNER/STORE_MANAGER/**FULFILLMENT** — unlike the other admin modules, fulfillment staff need this one) enforcing a real state machine (`ALLOWED_TRANSITIONS` in `orders.service.ts` — e.g. you can't jump `PENDING` straight to `DELIVERED`). Moving an order to `CANCELLED`/`REFUNDED` restocks inventory and reverses any loyalty points that order earned; both are terminal states with no outgoing transitions, which is what stops that reversal from double-firing. Editing items/address/pricing, internal notes, split shipment, packing slips, and shipping labels are still follow-up work.
- **Wishlist / Addresses / Saved Payment Methods** (`apps/api/src/modules/{wishlist,addresses,payment-methods}`) are the customer-account modules — all self-service (JWT-scoped to the caller, no RBAC), full CRUD, ownership-checked on every write (`findFirst({ id, userId })` before touching a row, so one customer can never read/edit/delete another's data — verified against a cross-user attempt during testing). Two things worth knowing: `Address.isDefault` is scoped **per `AddressType`** (one default shipping address, one default billing address, set independently), while `PaymentMethod.isDefault` is a single flag across all of a user's payment methods. And **saved payment methods only support Mobile Money** — `POST /account/payment-methods` rejects `CARD` with 501, the same as checkout; this API deliberately never accepts a raw card number, since there's no PCI-DSS gateway to hand it to yet and building a form that collects one to nowhere would be teaching a bad pattern.
- **HR** (`apps/api/src/modules/hr`) is a separate portfolio bolted onto the e-commerce platform — internal staff management, not customer-facing, and **not derived from the original wireframes/SRS** (there's no `FR-*` ID for it; it was scoped and approved directly with the user, phase by phase — see `docs/SRS.md` §18). All four phases are built.
  - **Phase 1** (Employee Profiles, Departments, Document Management, Staff ID cards): restricted to `OWNER`/`HR_MANAGER` (a role added specifically for this). `Employee` is deliberately **independent of `User`**, with only an optional 1:1 link — HR needs to hold a record for someone in recruitment/onboarding before (or even without) them ever getting a system login. `EmployeesService.update()` **diffs the incoming DTO against the current row and auto-logs an `EmploymentHistoryEntry`** for job-title/department/salary/status changes — that audit trail is the actual point of employment history, so don't bypass it with a raw `prisma.employee.update()` elsewhere. Employee records are **never hard-deleted**, only soft-terminated (`employmentStatus: TERMINATED`) — same legal/compliance-retention reasoning as orders, stronger here. `EmployeesService.getById()` takes the same optional-Prisma-client parameter as `CatalogService.getByIdForAdmin()`, for the same reason (transaction-visibility bug, see above) — pass `tx` through if you add another transactional write path. Staff ID cards are a pure frontend feature (`apps/admin/.../hr/employees/[id]/id-card`) — a CR80-sized (3.375in × 2.125in) printable view via `window.print()`, no PDF-generation library or physical card-printer integration.
    - **Department policy/permissions** (added later, per user request): every `Department` carries a `DepartmentPermission` row per `PermissionResource` (one per admin nav area — Products/Orders/Inventory/Customers/Marketing/CMS/Settings + each HR sub-area), each with `canView`/`canCreate`/`canUpdate`/`canDelete`/`canExecute` booleans, editable via the Departments page's "Policy & Permissions" panel (`PATCH /hr/departments/:id/permissions`). **This is a stored policy record, not the enforcement mechanism, by explicit user decision** — the API's real security boundary is still `RolesGuard` checking `UserRole` on every endpoint (see the Access Control note above); this table exists so departments have documented, editable, database-backed policy without redoing the tested role-based authorization. `DepartmentsService.create()` always creates a complete 15-row matrix (one per `PermissionResource`) — any resource not explicitly set starts deny-all — so the UI never has to handle a missing row. Seed data pre-populates the four real departments (Executive/Human Resources/Retail Operations/Fulfillment & Logistics) to mirror the actual `@Roles()` enforcement exactly (Executive: all-true everywhere; Human Resources: all-true on HR resources only; Retail Operations: all-true on operational admin resources, deny on Settings/HR; Fulfillment: view-only on operational admin resources plus `canExecute` on Orders, matching their one real write exception — order-status transitions), guarded by a row-count check so re-seeding never clobbers permissions edited later through the UI.
  - **Phase 2** (Time & Attendance, Leave, Shift Scheduling): every sub-feature has a **self-service side** (`/hr/me/*` routes, `MyAttendanceController`/`MyLeaveController`/`MyShiftsController`) open to *any* authenticated staff user — not role-gated like the rest of HR — plus an **admin/oversight side** (`/hr/attendance`, `/hr/leave-requests`, `/hr/shifts`) restricted to `OWNER`/`HR_MANAGER`. Self-service resolves "which employee is this?" via `EmployeesService.getByUserId(userId)`, which 404s with a clear message if the caller has no linked `Employee` — that's a real, expected case (e.g. a `SUPPORT_AGENT` account with no HR profile), not a bug. Mirrored in the admin frontend nav as "Human Resources" (oversight) vs. "My HR" (self-service) — both sections are visible to everyone; the pages themselves 403/404 appropriately. Clock-in is **web-only** — no biometric hardware/vendor SDK exists to integrate with, per user decision. Leave balance (`LeaveService.balance()`) is **computed on read**, not a stored counter, from approved `ANNUAL` requests in the target year vs `Employee.annualLeaveDaysPerYear` (default 21 — Uganda's Employment Act 2006 statutory minimum) — it's surfaced to inform an approve/reject decision, not hard-enforced, so HR can still approve past it. Shift swap approval (`ShiftsService.reviewSwapRequest()`) **reassigns the shift's `employeeId` to the covering employee** inside the same transaction as the status update — verified end-to-end that the shift actually moves, not just the swap-request status.
  - **Phase 3** (Performance Tracking, Self-Service Portal, Onboarding & Recruitment): `PerformanceService` (goals/feedback/reviews) uses **non-role-based authorization** — a deliberate one-off in HR — via `assertCanManage(callerUserId, callerRole, targetEmployeeId)`: `OWNER`/`HR_MANAGER` can manage anyone, but any other authenticated user can also manage records for employees where `Employee.managerId` points at their own linked `Employee` row, since performance management is a line-manager responsibility rather than an HR-exclusive one. A submitted review (`status: SUBMITTED`) locks its content — only the employee's own `acknowledge()` call (`/hr/me/reviews/:id/acknowledge`) can move it to `ACKNOWLEDGED`; no further HR edits once submitted. Self-service profile edit (`/hr/me/profile`, `MyProfileController`/`EmployeesService.updateMyProfile()`) intentionally excludes `jobTitle`/`departmentId`/`baseSalaryUgx` — the DTO whitelist rejects them outright rather than silently ignoring them. Recruitment's `RecruitmentService.convertToEmployee()` **reuses `EmployeesService.create()`** rather than duplicating employee-creation logic, so a converted applicant gets the same auto-generated employee number and auto-logged `HIRED` `EmploymentHistoryEntry` as a directly-hired employee; conversion also auto-transitions the `JobPosting` to `FILLED` and is guarded against double-conversion via `Applicant.convertedEmployeeId`. No e-signature/digital-paperwork workflow — conversion is a data-entry action.
  - **Phase 4** (Payroll, HR Dashboards, Productivity Metrics): `modules/hr/payroll/paye-nssf.util.ts` is a pure, Prisma/Nest-free arithmetic module (unit-testable in isolation) implementing Uganda's resident-individual monthly PAYE bands, the 5%/10% employee/employer NSSF split, overtime pay (`calculateOvertimePay()`), and 13th-month proration (`monthsEmployedInYear()`) — **its PAYE/NSSF rate constants are real, currently-published tax figures with real financial/legal consequences**; the file header says any rate change, or any real (non-demo) payroll run, needs accountant/tax-advisor sign-off first, don't touch those numbers casually. `computePayslip()` takes a full `PayslipInputs` (basic + taxable/non-taxable allowances + overtime + bonus + penalty + advance repayment) and computes PAYE on chargeable income (basic + taxable allowances + overtime + bonus — deliberately *not* the full gross) while NSSF is computed on `basicSalaryUgx` only, a documented simplification so allowances/bonuses don't silently change the statutory contribution.
    - **Recurring allowances**: `EmployeeAllowance` (housing/transport/lunch/medical/hardship/other, each `taxable` or not), CRUD via `AllowancesService`/`AllowancesController` at `/hr/employees/:employeeId/allowances`, applied to every regular run while `active`.
    - **Overtime**: computed *and* HR-confirmed, per user decision — `PayrollService.overtimePreview()` sums worked hours per day from `TimeEntry` against `Employee.standardHoursPerDay`, converts the excess via `calculateOvertimePay()` using `Employee.overtimeRateMultiplier`, and returns it as a suggestion only; nothing is paid until HR reviews it and creates (or edits, by deleting and re-adding) an `OVERTIME` `PayrollAdjustment` with the confirmed amount.
    - **Bonus/penalty/other one-off items**: `PayrollAdjustment` rows (`BONUS`/`PENALTY`/`OVERTIME`/`OTHER_EARNING`/`OTHER_DEDUCTION`) via `createAdjustment()`/`removeAdjustment()`, blocked once the period is `FINALIZED`. Deduction types (`PENALTY`/`OTHER_DEDUCTION`) always subtract post-tax from net pay regardless of their `taxable` flag.
    - **Salary advances (auto-recovery)**, per user decision: `SalaryAdvance` is a running ledger (principal/installment/`balanceRemainingUgx`). `PayrollService.run()` *previews* each active advance's due installment (`min(installment, balance)`) and snapshots it per-payslip as `PayslipAdvanceRepayment` rows — the ledger itself is untouched. Only `finalize()` actually decrements `balanceRemainingUgx` (marking `PAID_OFF` at zero) inside its `$transaction`, which is what keeps re-running a not-yet-finalized period idempotent — verified end-to-end that re-running doesn't double-deduct and finalizing exactly once does.
    - **13th month cheque**: `runThirteenthMonth(year)` creates/reuses a `PayrollPeriod` with `type: THIRTEENTH_MONTH` (the `@@unique([month, type])` compound key, replacing the old month-only uniqueness, is what lets a regular and a 13th-month period coexist in the same December). Pays `baseSalaryUgx × monthsEmployedInYear/12` through the same PAYE/NSSF pipeline, with allowances/overtime/bonus/advance-recovery deliberately excluded — a standalone prorated payout, not a regular run. Uganda has no statutory 13th-month law, so this is a discretionary benefit per the user's decision, not a compliance requirement.
    - `PayrollService.run()` still computes a `Payslip` per `ACTIVE`/`ON_LEAVE` employee with `baseSalaryUgx` set, inside a `$transaction` that deletes-then-recreates that period's payslips (cascading to their `PayslipAdvanceRepayment` rows) so re-running before finalization is safe; `PayrollPeriod.status` (`DRAFT` → `COMPUTED` → `FINALIZED`) gates both `run()` and adjustment mutation. Payslips snapshot every figure at computation time, deliberately not a live join to `Employee`/`EmployeeAllowance`, so later changes don't rewrite pay history.
    - `DashboardService.summary()` is pure read-aggregation (headcount, pending leave, open postings, clocked-in-now, documents expiring in 30 days, goal completion rate) over Phase 1-3 tables — no new stored metrics, same "compute on read" philosophy as `LeaveService.balance()`. No labor-cost/turnover/attendance-trend analytics beyond the goal-completion figure — flagged as future follow-up work, not started.
- **Most other modules are intentionally partial**: they implement the read-side queries that are simple Prisma calls (list inventory, list customers, list coupons, etc.), but skip business logic that has real design decisions pending — CMS's Blog Posts stays read-only (Social Media Accounts, Static Pages, and Banners all have real admin CRUD now — `modules/cms/admin-social-links.controller.ts`, `admin-pages.controller.ts`, `admin-banners.controller.ts` — the storefront homepage hero and `/pages/[slug]` actually render them), admin invites, OTP/biometric/social login. Each gap is marked with a comment pointing at the relevant SRS FR-ID. Grep `follow-up work` in `apps/api/src` to find all of them.
- **Frontend auth** uses a deliberately simple pattern: JWT tokens in `localStorage` via `lib/auth-client.ts` in each frontend app, set by the login/signup pages and read by an `authedFetch()` helper. This is called out in that file as a dev simplification — production should move to httpOnly cookies set by a server-side route handler.
- **Route structure** in both frontend apps uses Next.js route groups: a `(site)`/`(admin)` group with the "real" shell (header+footer, or the admin sidenav) and, in the storefront, a separate `(auth)` group with a minimal centered layout for login/signup/forgot/reset — matching the wireframes' distinct "standalone" auth-screen look.
- **Shared design tokens**: both frontend apps' `globals.css` define the same Tailwind v4 `@theme` color tokens (`--color-gold`, `--color-surface`, etc.) copied from the wireframes' CSS custom properties, so `bg-gold`, `text-gold-light`, etc. are available as utility classes in both apps. There's no shared package — each app defines its own copy, matching the wireframes' "every file is fully standalone" convention.
- **Next.js 16 caveat**: this version has App Router API differences from older training data (typed `PageProps<'route'>`/`LayoutProps<'route'>` helpers, async `params`/`searchParams`). Each app's `AGENTS.md` (auto-generated by `next dev`/`next build`, safe to leave in git) points at `node_modules/next/dist/docs/` — check there before assuming an older Next.js pattern still applies.

## Known environment quirks

- `create-next-app` auto-initializes a nested `.git` per app; if you ever re-scaffold a frontend app, delete the nested `.git` it creates before building — a nested repo confuses Turbopack's root detection (`Could not find the Next.js package` errors) and silently excludes that app's files from the monorepo's root git repo.
- Installing dependencies may trigger this environment's `npm approve-scripts` gate for packages with install scripts (currently `@prisma/client`, `@prisma/engines`, `prisma`, `unrs-resolver`). Run `npm approve-scripts <pkg>` for any newly-flagged package, then `npm install` again so the script actually runs (e.g. Prisma's engine-binary download).

## Design source material

`mockUps/` holds eight self-contained, static HTML wireframes the SRS and app were built from:

- `ChrisPa_Frontend_Wireframes.html` / `ChrisPa_Frontend_Wireframes__1_.html` — customer storefront (near-identical duplicates)
- `ChrisPa_Admin_Wireframes__1_.html` — backend/admin console
- `ChrisPa_Login_Wireframe.html`, `ChrisPa_SignUp_Wireframe.html`, `ChrisPa_ForgotPassword_Wireframe.html`, `ChrisPa_ResetPassword_Wireframe.html` — single-purpose auth screens
- `ChrisPa_MyAccount_Wireframes.html` — expanded account-area screens (profile, addresses, orders, loyalty, privacy)

Open any `.html` file directly in a browser (`file://` path) — each is fully self-contained (inline `<style>`/`<script>`, no build step, no external dependencies). Every wireframe reuses the same base template: CSS custom properties for the green/gold theme in `:root`, an `.app` → `.sidenav` + `.main` shell, and (for multi-screen files) client-side "page switching" via `<div class="page" id="page-{key}">` + `data-page` buttons + a `titles` lookup object — this is what the frontend apps' route groups replaced with real routing. `.annot` elements are wireframe-only annotations citing "Feature group N", which is what `docs/SRS.md`'s FR-IDs formalize.

`ChrisPa_Admin_Wireframes__1_.html` and both `ChrisPa_Frontend_Wireframes*.html` files each contain a second, orphaned copy of the page-switching JS pasted into the page body — dead markup, not a second live script.
